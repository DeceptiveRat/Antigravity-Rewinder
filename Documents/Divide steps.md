To achieve counterfactual replay from any arbitrary point in the artifact history, we must treat steps not just as text logs, but as distinct **state machine transitions**.

In Antigravity's architecture, steps fall into two overarching layers:
1. **Dialogue & Context Steps** (Direct communication and instructions)
2. **Tool Execution Pairs** (Where an action is requested by the model and executed by the environment)

Here is the complete taxonomy of steps we need to consider, with tool calls divided by their underlying operational behavior and side effects.

---

### Layer 1: Dialogue & System Context Steps

These steps define conversational agency and context boundaries.

1. **`USER_INPUT` (User Prompts & Commands)**
   * Represents user instructions, follow-up messages, or responses to questions.
   * *Replay requirement*: When rewinding to a user input, execution resumes by querying the model with the prior context plus this prompt.

2. **`PLANNER_RESPONSE` (Assistant Thoughts & Messages)**
   * Contains internal chain-of-thought deliberation (`<THINKING>` / `thinking` field) and final text directed to the user.
   * *Replay requirement*: Generated by the model in response to prior conversation or tool results.

3. **`SYSTEM_MESSAGE` / `EPHEMERAL_MESSAGE` / `CONVERSATION_HISTORY`**
   * Reminders, tool guidelines, or summaries injected by the platform runtime without explicit user input.
   * *Replay requirement*: Static context seeded into the prompt prefix.

---

### Layer 2: Tool Calls (Categorized by Operational Mechanics)

Every tool interaction consists of a **Pair**:
* **Tool Invocation (`TOOL_CALL`)**: The model decides to run a function and outputs its name and arguments.
* **Tool Observation (`TOOL_RESULT`)**: The local runtime executes the tool and writes back the output (recorded as `GENERIC` / `132` in the database).

To make execution resume from a tool call, we must handle tools based on their execution mechanics and side-effect profile:

#### Category A: File System Read Tools (Passive / Read-Only)
* **Tools**: `view_file`, `list_directory`, `grep_search`, `find_by_name`
* **Behavior**: Reads text slices, directory listings, or regex matches from disk.
* **Side effects**: Zero disk mutations.
* **Counterfactual challenge**: Highly deterministic. To replay, the harness only needs to re-read the specified file path or directory and format the tool result.

#### Category B: File System Mutation Tools (State Altering)
* **Tools**: `write_to_file`, `replace_file_content`
* **Behavior**: Creates new files, overwrites existing files, or performs contiguous line replacements.
* **Side effects**: Directly mutates the project directory.
* **Counterfactual challenge**: If you rewind to before a write tool, **the file on disk might still contain the changes made during the first run**. Replay requires resetting the workspace file state (e.g., via git or filesystem snapshots) to match the exact turn being tested.

#### Category C: Terminal & Shell Execution Tools (Arbitrary Process Execution)
* **Tools**: `run_command`, `send_command_input`
* **Behavior**: Spawns a subshell process (bash/zsh) to execute arbitrary commands (compilation, running scripts, git operations, package installations).
* **Side effects**: Can modify files, start background processes, alter system state, or rely on environment variables.
* **Counterfactual challenge**: To replay, the command must be re-executed in the shell with the exact working directory (`cwd`) and environment flags recorded in the invocation payload.

#### Category D: Web & Network Retrieval Tools (External Knowledge)
* **Tools**: `read_url_content`, `search_web`, `read_browser_page`
* **Behavior**: Performs outbound HTTP requests, queries search engines, or launches headless browser sessions.
* **Side effects**: No local disk changes, but depends on live external web servers.
* **Counterfactual challenge**: External websites may change, experience downtime, or rate-limit requests. For strict counterfactual replay, we have to decide whether to re-fetch live over the network or mock the response using the recorded artifact.

#### Category E: Interactive User Inquiry Tools (Human-in-the-Loop)
* **Tools**: `ask_question`
* **Behavior**: Pauses agent execution and renders an interactive prompt or multiple-choice modal in the UI.
* **Side effects**: Transfers execution control back to the human.
* **Counterfactual challenge**: Replay cannot proceed automatically without either human intervention or a recorded synthetic answer.

#### Category F: Multi-Agent & Subagent Orchestration Tools (Recursive Trajectories)
* **Tools**: `invoke_subagent`, `send_message`, `manage_subagents`
* **Behavior**: Spawns isolated child agent sessions that create their own separate SQLite database files and workspaces.
* **Side effects**: Creates parent-child dependency links (`parent_references` table) and cross-conversation message passing.
* **Counterfactual challenge**: Rewinding a step that invoked a subagent requires managing the state of both the parent database and the child database simultaneously.

#### Category G: Background Task & Daemon Management Tools (Asynchronous Execution)
* **Tools**: `manage_task`, `schedule`
* **Behavior**: Monitors long-running tasks, sets timers, or manages cron schedules.
* **Side effects**: Background process queues and task logs in `.system_generated/tasks/`.
* **Counterfactual challenge**: Requires handling asynchronous signals and task completion notifications.

---

### Recommended Next Step

Since each tool category behaves differently, we should start with the simplest category and build up:
1. **Category A (Read-only tools like `view_file`)**: The step you just tested. Because there are no side effects on disk, it is the cleanest sandbox to build the mid-turn execution harness.
2. **Category B (Write tools) & Category C (Shell commands)**: Adding workspace restoration alongside database rewinding.
3. **Category D through G**: Handling network, subagents, and async tasks.
